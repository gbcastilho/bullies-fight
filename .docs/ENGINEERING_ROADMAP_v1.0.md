## 1. Interaction Contract — How Mentorship Works

Zero code generation, forever. Under no circumstances will mentorship provide source code, pseudocode, data definition language, data manipulation language, Dockerfiles, compose files, Kubernetes manifests, configuration file contents, or ready to paste commands.

Guidance is Socratic and conceptual only. When code is shared or debugging help is requested, mentorship responds with high level architectural patterns, questions that redirect attention to the likely failure area, and pointers to official documentation by title. At most, a documentation page title or a public concept name may be named so the builder can look it up independently.

Interview gates are oral defenses. At the end of every stage, mentorship acts as a technical interviewer asking whiteboard style questions, what if placement questions, and why this approach questions. Verdicts are Pass or Retry With Pointer. Retry never includes a fix, only a question and a documentation direction.

Result over procedure. Acceptance criteria describe observable results, not steps to type. If a criterion says a failure is survived, it describes what must remain true in logs, dashboards, and durable state, not how to trigger the failure keystroke by keystroke.

## 3. Global Locks — Decisions That Prevent Future Rework

These were grilled and locked before v1.0. They exist so the roadmap never churns.

Game scope: three versus three arena matches, exactly like Brawl Stars team size. Six players per arena room. Short ephemeral matches of a few minutes. Fast top down movement and shooting. Best practice lobby flow with account creation, matchmaking queue, arena assignment, result recording, and ranking progression.

Authority and transport lock: authoritative server simulation at twenty ticks per second over persistent WebSocket connections. Clients send intents, server simulates and broadcasts authoritative snapshots. Client side prediction and reconciliation are explicitly out of scope until the final stretch discussion, to keep early stages learnable. Positions and in flight inputs are ephemeral. Accounts, matchmaking rating, match results, and progression are durable.

Stack evolution lock: start with Node with TypeScript plus Fastify plus PostgreSQL plus Docker. Progressively introduce one infrastructure primitive per stage from the proven set: structured logging, Prometheus with Grafana, Redis compatible presence store, NATS event bus, reverse proxy load balancer, Toxiproxy style network fault injector. No other core language or framework change is allowed. This keeps failure causes attributable to architecture, not to stack churn.

Hardware and infra ceiling lock: single laptop with twelfth generation Intel Core i5 with twelve threads, sixteen gigabytes of RAM, two hundred fifty six gigabytes of SSD, plus discrete laptop GPU which is irrelevant for backend work. No cloud environment. All proof runs on a single Docker Compose topology on one host, using separate Docker networks plus fault injection to simulate partitions and latency. Lightweight single node Kubernetes and multi host cloud are explicitly out of scope. This is honest distributed learning under constraint.

Scale target lock: twenty concurrent matches with six players each, meaning one hundred twenty concurrent real or simulated clients, plus one hundred headless bots for soak. Anything higher will exhaust sixteen gigabytes and produce misleading out of memory failures instead of distributed lessons.

Failure semantics lock, option A only: if a game server node dies, the matches hosted on that node die cleanly with it. Players return to lobby without matchmaking rating penalty, lobby and ranking remain unaffected, and requeue succeeds. Live migration of an in progress match to a survivor node is explicitly out of scope and will not be added later. This matches the genre norm for short matches and keeps the resilience problem focused on isolation and durability rather than state transfer.

Observability path lock: start with simple but structured logs in machine readable form, then add numeric metrics viewable as graphs, then add traces in advanced stages only if needed. Logs answer what happened. Metrics answer how often and how slow. Traces answer where time went across services. No stage jumps ahead.

Learning diet lock: official documentation first plus one deepening reference per stage. Baseline self ratings assumed as networking three of five, PostgreSQL four of five, Docker networking one of five, Node event loop two of five. Therefore Docker and Node internals are paced gently with extra fundamentals, while PostgreSQL topics move faster. Order is prerequisites first. No stage introduces consensus before the builder has felt state loss. No stage introduces partitioning before the builder has operated replication and presence.

Gate rubric lock: every gate judges three lenses. Explain means the builder can whiteboard the mechanism from memory. Decide means the builder can justify the chosen approach versus at least one alternative and name the accepted trade off. Predict means the builder can name what breaks under death, partition, or overload and what evidence would prove recovery. Code acceptability is judged through behavior and proof, never through code review. Evidence is structured logs, metric graphs, durable database state, and orchestrator status described in words.

## 4. End State Vision — Where Stage Seven Lands

A reverse proxy load balancer fronts stateless HTTP entry points for accounts, queue join, and health. A dedicated matchmaking service owns queue and room assignment. Multiple sharded authoritative game server nodes each host many concurrent arena rooms, partitioned by match identifier using consistent hashing so room placement is deterministic and rebalancing is bounded. A Redis compatible store owns ephemeral presence, heartbeat liveness, and room to node mapping. A NATS style event bus decouples match lifecycle events from persistence so game ticks never block on database writes. PostgreSQL owns all durable state with clear transaction boundaries and idempotent consumers. Prometheus with Grafana shows golden signals per service plus game specific signals such as tick deviation, input backlog, match abort rate, and requeue success rate. Any game node can be terminated mid match with lobby and ranking unaffected and with clean abort semantics. Partitions and latency can be injected between any two logical groups and the system degrades openly rather than silently corrupting state.

## STAGE ZERO — NAIVE MONOLITH BUILT TO DIE

Timebox: one week.

### Scenario

Build the simplest thing that plays. One Fastify process serves account endpoints, matchmaking queue, and authoritative arena simulation for all matches in memory. One PostgreSQL database exists but is used minimally, for example only for accounts. All match state lives in process memory. All clients connect to the single process. Docker Compose runs the app plus the database on one network. No presence store, no event bus, no load balancer, no metrics graphs. Structured logging is minimal on purpose.

Deliberately include naive choices: global in memory match map with no eviction policy, no graceful shutdown handling, no heartbeat timeout, blocking persistence calls on the tick path if convenient, no backpressure on inbound intents. The goal is not quality. The goal is a baseline that demonstrably collapses.

### The Why, Pain Point

This stage exposes the single point of failure, fate sharing, and state loss. If the process dies, every match and every queued player dies with it. If the event loop stalls, every room stutters together. If memory grows, every room degrades together. Without this felt pain, later decoupling looks like ceremony rather than survival. It also exposes the absence of observability: when everything fails at once with only plain text logs, root cause is guesswork.

### Concepts To Study, In Order

1. Authoritative server and fixed tick simulation, why the server is the source of truth and what a tick means.
2. WebSocket as long lived full duplex transport over TCP, head of line blocking intuition, and why twenty Hertz is a reasonable starting cadence.
3. Node event loop fundamentals, timers, and starvation, why one slow handler delays all rooms.
4. Process fate sharing and single point of failure, blast radius reasoning.
5. Ephemeral versus durable state, what may be lost versus what must never be lost.
6. Docker image versus container versus network versus volume, at the level needed to run two services locally, since Docker baseline is one of five.

### Sources

Use Fastify official documentation for routing and lifecycle, Node event loop official documentation for timers and phases, Docker networking and Compose official documentation for services and networks, PostgreSQL documentation introduction for roles and durability basics, plus one deepening chapter on the single process bottleneck from Designing Data Intensive Applications, early chapters on reliability and models. If video helps, choose one conference talk on authoritative game servers, but docs remain primary.

### Acceptance Criteria

- A single app container plus a single database container start from Compose and remain up for a full match with six simulated players moving and shooting with visible authoritative updates.
- With at least two concurrent matches running, terminating the app container mid match produces total loss: no match can continue, lobby is unavailable until restart, and restarted state shows no surviving in memory matches while durable accounts remain.
- Under a modest bot flood beyond the scale target for this stage, tick cadence visibly degrades for all rooms together rather than isolating, proving fate sharing. Evidence is described through structured log excerpts in words plus observed tick deviation, not through pasted logs.
- A one page written postmortem exists describing the single point of failure, what was lost versus retained, and why horizontal scaling is impossible in this shape.

### Interview Gate, Example Questions

- Whiteboard how a client intent flows from socket to simulation to broadcast in this monolith, and where a slow handler harms all rooms.
- What would happen if the database became slow while persistence is called on the tick path, and why does fate sharing make it worse.
- Why did you place match state in memory rather than in the database, and what did that choice cost you when the process died.
- What single change would least fix availability, and why would it still leave a single point of failure.

### Anti-goals With Why

- Do not add Redis, event bus, load balancer, or metrics graphs yet. Why: you have not yet felt the outage those tools mitigate, so you would misconfigure them without understanding.
- Do not add Kubernetes or multi host networking yet. Why: orchestration hides failures behind restarts you have not learned to diagnose, especially with a Docker baseline of one.
- Do not optimize tick performance yet. Why: premature tuning masks architectural fate sharing with micro improvements.

## STAGE ONE — OBSERVABILITY BEFORE SCALE

Timebox: two weeks.

### Scenario

Keep the monolith topology, but make it observable. Introduce structured machine readable logs with consistent fields for match identifier, player identifier, tick number, and outcome. Add numeric metrics exposed for scraping and viewable as graphs in Grafana with a Prometheus style backend. Track golden signals per endpoint plus game specific signals such as tick deviation from the twenty Hertz target, inbound intent backlog depth, match count, connected client count, and persistence latency. Add basic health endpoints that distinguish liveness from readiness in meaning, even if both are served by the single process. Keep one game process. No scaling yet.

### The Why, Pain Point

This stage solves flying blind. Stage Zero failures were arguable. Stage One failures become measurable. It teaches the difference between logs, metrics, and traces, and why alerts need numbers with thresholds rather than text search. It also exposes observer overhead and cardinality danger: naive per player or per tick labels can explode metric storage on a sixteen gigabyte host. Learning to observe before scaling prevents scaling a mystery.

### Concepts To Study, In Order

1. Structured logging, fields, levels, and correlation identifiers for match and player.
2. Metrics types: counters, gauges, histograms, and summaries, and when each lies if misused.
3. Golden signals: latency, traffic, errors, saturation, plus game signals like tick deviation and backlog.
4. Liveness versus readiness, why a process can be alive but unready to take matches.
5. Cardinality and retention, why unbounded label values exhaust a laptop.
6. Dashboard hygiene, one graph per question, no vanity graphs.

### Sources

Use Prometheus documentation on metric types and exposition, Grafana documentation on dashboards and alerting concepts, OpenTelemetry documentation introduction for the logs metrics traces distinction, Node diagnostics documentation for event loop lag intuition, plus one deepening chapter on monitoring from a site reliability engineering text. Keep Docker study focused on volume persistence for metric storage.

### Acceptance Criteria

- Every match lifecycle transition and every persistence outcome is traceable by match identifier across logs without free text search, described by field names in words.
- Grafana shows at least latency, error rate, tick deviation, backlog depth, and saturation for the single node over a full multi match run, with visible degradation during a bot flood.
- A misconfigured high cardinality label experiment is documented and then removed, with a written note on storage and query cost observed on the laptop.
- Liveness remains affirmative during overload while readiness correctly reports inability to accept new matches, proving the distinction is real.

### Interview Gate, Example Questions

- Whiteboard the path from tick measurement to graph, and explain why a histogram answers tail latency while an average hides it.
- What would happen if every tick number became a metric label, and how would you detect the damage on sixteen gigabytes.
- Why did you choose these five graphs as the minimal survival set, and what decision would each graph drive.
- What remains invisible even now, and which future primitive will reveal it.

### Anti-goals With Why

- Do not shard or add nodes yet. Why: you need a clean baseline graph of one node under stress to compare against horizontal behavior later.
- Do not add distributed tracing across services yet. Why: there is only one service, tracing now adds cost without teaching cross service causality.
- Do not alert on every anomaly yet. Why: alert fatigue on a learning system teaches muting rather than diagnosis.

## STAGE TWO — STATE SEPARATION AND DURABILITY

Timebox: two weeks.

### Scenario

Keep one game process, but draw a hard line between ephemeral and durable. Match positions, velocities, cooldowns, and in flight intents remain in memory only. Accounts, matchmaking rating, match records, inventories if any, and progression move to PostgreSQL with explicit transaction boundaries and constrained access patterns. Game ticks never wait synchronously for durability. Match end flows through a clear commit point where results are recorded once. Add heartbeat based liveness so dead sockets are reaped and abandoned matches are closed deterministically. Add startup recovery semantics: on restart, durable state is intact, ephemeral matches are gone by design and reported as such.

### The Why, Pain Point

This stage exposes state loss versus durability confusion, partial writes, and race conditions on match commit. It teaches atomicity and idempotency at the exact moment two clients finish a match at once or a retry double submits a result. It also exposes backpressure neglect: if persistence slows, the tick loop must shed or queue responsibly rather than stall all rooms. PostgreSQL strength rated four of five is leveraged here, while Node backpressure rated two of five is deliberately exercised.

### Concepts To Study, In Order

1. Transactions, atomicity, and isolation levels at the level needed for match result commits.
2. Idempotency keys and exactly once effect versus at least once delivery, why retries are safe only with idempotent receivers.
3. Write ahead log intuition and crash recovery, what survives a container termination.
4. Heartbeats, timeouts, and failure detection, why dead clients must be reaped by the server.
5. Backpressure and load shedding, queues with bounds versus unbounded growth.
6. Timeouts and deadlines on outbound database calls so ticks survive slow persistence.

### Sources

Use PostgreSQL documentation on transactions, isolation, and crash recovery, Fastify documentation on request lifecycle and error handling, Node documentation on timers and asynchronous scheduling, plus one deepening chapter on exactly once effects from Designing Data Intensive Applications. Add one paper introduction on timeouts and failure detectors for vocabulary, skim only.

### Acceptance Criteria

- Killing the app mid match loses in memory positions by design, but accounts, ratings, and completed match histories remain intact and queryable after restart.
- Double submission of the same match result, caused by retry, records a single durable outcome with no rating drift, verified by rating totals before and after the retry storm described in words.
- A slow persistence fault causes bounded queueing with visible shedding or deferral while tick cadence for live rooms remains within a declared deviation budget, rather than freezing all rooms.
- Dead socket simulation results in deterministic reap and match closure with a structured log trail correlatable by match identifier.

### Interview Gate, Example Questions

- Whiteboard the commit point for match end and show where a crash leaves a half written result, then explain how your boundary prevents it.
- What would happen if two result submissions for the same match arrived concurrently, and why does your idempotency approach make the second safe.
- Why did you keep positions out of the database, and what alternative did you reject and why.
- What would happen if persistence latency grew tenfold during a live match, and where would backpressure appear first.

### Anti-goals With Why

- Do not introduce Redis or an event bus yet. Why: you must first feel synchronous durability pain and solve it with boundaries and idempotency, otherwise the bus becomes a hidden database.
- Do not add multiple game nodes yet. Why: concurrent writers to the same match would confuse the durability lesson with a coordination lesson.
- Do not tune PostgreSQL for production scale yet. Why: laptop durability semantics matter more now than throughput tuning.

## STAGE THREE — HORIZONTAL GAME NODES WITH PRESENCE AND LOAD BALANCING

Timebox: two to three weeks.

### Scenario

Run multiple authoritative game server nodes behind a reverse proxy load balancer for HTTP, with sticky affinity for WebSocket upgrade by match assignment rather than by client round robin. Introduce a Redis compatible store for ephemeral presence: which players are online, which match lives on which node, heartbeat liveness with expiry, and room to node mapping. HTTP entry points stay thin. Matchmaking assigns a match identifier and a node owner, records the mapping with expiry, and directs clients accordingly. No event bus yet. PostgreSQL remains the durable store. This is the first truly multi process stage, still on one host via Compose with separate logical networks to keep failure domains visible.

This stage assumes Docker networking fundamentals are now solid, addressing the initial one of five rating through deliberate practice with multiple services, aliases, and network segmentation.

### The Why, Pain Point

This stage exposes sticky state, uneven load, split presence, and partial failure. It teaches why naive round robin breaks long lived sockets, why presence needs expiry rather than explicit logout, and why a load balancer health check must reflect game readiness rather than mere socket accept. It also exposes thundering herd on restart and hotspot matches where one heavy room starves its node siblings.

### Concepts To Study, In Order

1. Layer seven routing versus layer four balancing, and sticky affinity by match identifier.
2. Presence with heartbeats and time to live expiry, why Explicit logout is insufficient.
3. Health checking, active versus passive, and readiness that considers tick health and backlog.
4. Consistent hashing intuition for match to node mapping and bounded reassignment.
5. Hotspots and noisy neighbors on shared nodes, mitigation by match placement limits.
6. Docker networks and service discovery on Compose, aliases and segmentation for failure clarity.

### Sources

Use reverse proxy load balancer official documentation for routing and health checks, Redis style store documentation for expiry and presence patterns, Docker networks official documentation for segmentation and aliases, Fastify documentation for graceful connection handling, plus one deepening chapter on partitioning and load balancing from Designing Data Intensive Applications.

### Acceptance Criteria

- At least three game nodes plus load balancer plus presence store plus database run together on Compose and host at least six concurrent matches with correct match to node mapping visible in presence described in words.
- Terminating one game node mid match aborts only its hosted matches cleanly while other nodes continue unaffected, lobby remains available, and affected players can requeue without rating penalty.
- Presence expiry correctly marks terminated node matches as dead within a declared time bound without manual cleanup, and stale mappings never route new clients to the dead node after expiry.
- A hotspot experiment with one intentionally heavy match shows degraded ticks isolated primarily to its node with measurable but bounded impact on sibling matches on the same node, documented with graph comparison in words.

### Interview Gate, Example Questions

- Whiteboard how a new player flows from queue to presence to node assignment to socket, and where a stale mapping would misroute.
- What would happen if presence expiry were twice as long and the balancer health check ignored tick backlog, and which user visible failure would result.
- Why did you choose match identifier affinity over client round robin, and what alternative placement did you reject.
- What would happen if all clients reconnected at once after a balancer restart, and how does your design avoid a thundering herd.

### Anti-goals With Why

- Do not add an event bus yet. Why: synchronous cross service calls must first reveal coupling pain so the bus solves a felt problem.
- Do not attempt live match migration yet, and per lock never. Why: clean abort plus requeue is the required genre appropriate resilience, migration would explode scope.
- Do not introduce autoscaling yet. Why: fixed node counts teach placement and hotspot reasoning that autoscalers would obscure.

## STAGE FOUR — DECOUPLING WITH EVENTS AND DEDICATED MATCHMAKING

Timebox: two weeks.

### Scenario

Extract matchmaking into a dedicated service and decouple lifecycle with an event bus. Game nodes publish match lifecycle events such as match started, match ended, match aborted, and player events. A persistence consumer subscribes and writes durable outcomes idempotently to PostgreSQL. Matchmaking subscribes to capacity and result signals to improve placement. Game ticks never block on cross service calls. The bus carries facts, not commands, with versioned event envelopes and backward compatible evolution. Presence remains in the Redis compatible store. Load balancer remains for HTTP. Everything still runs on Compose on one host.

### The Why, Pain Point

This stage exposes temporal coupling, cascading slowness, and poison messages. If persistence slows, game ticks must remain healthy while the consumer lags openly with a visible backlog. If a malformed event arrives, one bad message must not halt the consumer forever. If event order varies, rating updates must remain correct. It teaches at least once delivery with idempotent consumers as the sane default and why exactly once delivery is not promised by the bus.

### Concepts To Study, In Order

1. Events versus commands and запросов, facts with versions versus instructions.
2. At least once delivery, redelivery, and idempotent consumers.
3. Consumer groups, offsets or durable subscriptions, and replay for recovery.
4. Poison messages, dead letter handling, and schema evolution.
5. Backpressure across services via bounded consumer lag and visible backlog metrics.
6. Outbox intuition, why game state and published facts must agree without distributed transactions, at an introductory level.

### Sources

Use NATS official documentation for subjects, streams, consumers, and delivery guarantees, Redis style documentation only for presence refreshers, PostgreSQL documentation for idempotent upserts conceptually, plus one deepening chapter on messaging semantics from Designing Data Intensive Applications. Add one article on outbox pattern for vocabulary, skim only.

### Acceptance Criteria

- With persistence consumer paused, live matches continue with healthy ticks while consumer lag grows visibly on graphs, and on resume all pending outcomes are applied exactly once in effect with no rating drift.
- A malformed event is isolated to dead letter handling with consumer continuity preserved and a structured log trail correlatable by event identifier described in words.
- Replaying recent events after a consumer crash recovers without duplicate durable effects.
- Matchmaking placement decisions remain correct under consumer lag, never assigning to a dead node based on stale presence, verified by mapping checks described in words.

### Interview Gate, Example Questions

- Whiteboard the event flow for match end and show where a crash between publish and write could duplicate, then explain why the effect remains single.
- What would happen if event order inverted for two updates to the same player, and why does your consumer remain correct.
- Why did you choose facts with versions over remote commands, and what coupling did you remove.
- What would happen if the bus itself became slow, and where would a player first notice versus where would an operator first notice.

### Anti-goals With Why

- Do not add distributed transactions across services. Why: they couple availability to the slowest participant and contradict the decoupling lesson.
- Do not build a generic event framework yet. Why: a small versioned envelope for three lifecycle events teaches evolution without framework magic.
- Do not add tracing across every hop yet unless needed. Why: lag and dead letter visibility answer more questions now with less overhead on the laptop.

## STAGE FIVE — RESILIENCE, RETRIES, SHUTDOWN, AND HIGH AVAILABILITY HABITS

Timebox: two to three weeks.

### Scenario

Harden the multi service topology for everyday failure without adding new topology. Introduce disciplined timeouts with deadlines on every cross service call, bounded retries with exponential backoff and jitter for idempotent operations only, circuit breaking intuition at the load balancer and client level, bulkheads by capping matches per node, and graceful shutdown that drains sockets and finishes in flight ticks before exit. Presence heartbeats, bus subscriptions, and database pools all close cleanly. Add chaos drills limited to process termination and slow dependencies, not yet partitions. PostgreSQL runs with persistent volumes and documented backup and restore check, still single instance. No sharding yet.

### The Why, Pain Point

This stage exposes retry storms, cascading failure, and unclean shutdown loss. Naive immediate retries amplify a slow dependency into a full outage. Missing deadlines propagate slowness from persistence to ticks to balancer to clients. Ungraceful termination drops in flight results and corrupts presence. It teaches that high availability is mostly habits: bounds everywhere, idempotency before retries, and shutdown as a first class state.

### Concepts To Study, In Order

1. Timeouts, deadlines, and budgets across hops.
2. Retry safety, idempotency precondition, backoff with jitter to avoid synchronized retries.
3. Circuit breaking and load shedding, failing fast to protect the whole.
4. Bulkheads and concurrency caps per node and per pool.
5. Graceful shutdown: drain, finish, close, exit, and readiness flap during deploy.
6. Backup and restore fundamentals for single instance durability confidence.

### Sources

Use resilience pattern documentation from a recognized site reliability text, NATS and Redis style client documentation sections on timeouts and reconnect behavior, PostgreSQL documentation on persistence and backup concepts, Node documentation on signal handling conceptually, plus one deepening article on cascading failures and backoff. Keep Docker study on restart policies and signal propagation.

### Acceptance Criteria

- A slow durable dependency drill shows bounded retries with jitter and no retry storm on graphs, with tick health preserved and consumer lag recovering openly after the fault clears.
- A rolling restart of game nodes one by one preserves lobby availability throughout, aborts only matches on the restarting node by design, and leaves no stale presence after a declared expiry bound.
- An unclean termination drill versus a graceful drain drill shows a measurable difference in lost in flight results and presence staleness, documented in words with metric comparison.
- A database volume removal and restore check proves that accounts and histories survive operator error, with a written recovery note.

### Interview Gate, Example Questions

- Whiteboard where every timeout and retry lives in your topology and which operation is explicitly non retryable and why.
- What would happen if retries had no jitter during a synchronized reconnect, and how would graphs reveal the storm.
- Why did you cap matches per node rather than trusting the scheduler, and what hotspot did the cap prevent.
- What would happen if shutdown skipped draining, and which durable invariant would break first.

### Anti-goals With Why

- Do not add multi instance database or sharding yet. Why: retry and shutdown habits must be correct on a simple store before replication multiplies failure modes.
- Do not inject network partitions yet. Why: process death and slowness teach bounded recovery first, partitions add split brain reasoning too early.
- Do not autoscale yet. Why: caps and shedding teach capacity honesty that autoscaling would postpone.

## STAGE SIX — PARTITIONING, PLACEMENT, AND NETWORK CHAOS

Timebox: two to three weeks.

### Scenario

Partition deterministically and then break the network on purpose. Finalize match to node placement by match identifier with consistent hashing and a declared bound on reassignment during node membership change. Segment Compose into logical networks for edge, game nodes, presence, bus, and durability to make partitions injectable. Introduce a Toxiproxy style fault injector to add latency, loss, and full partitions between logical groups. Drills include presence partition from game nodes, bus partition from persistence, balancer partition from one game node, and latency injection on the durable path. System must degrade openly: affected matches abort cleanly, unaffected matches continue, no silent rating corruption, no phantom presence, no duplicate durable effects on heal.

### The Why, Pain Point

This stage exposes network partitions, split brain presence, and partial availability. It teaches the core distributed trade off: under partition, choose availability of unaffected matches plus consistency of durable outcomes, with explicit unavailability for the affected slice. It exposes why expiry based presence beats authoritative presence during partitions, why consumers must remain idempotent on heal with redelivery bursts, and why operator graphs must distinguish partitioned from merely slow.

### Concepts To Study, In Order

1. Consistent hashing, membership, and bounded reassignment.
2. CAP and PACELC intuition, what is sacrificed during partition versus during healthy latency.
3. Quorum intuition and why single instance durability plus expiry is chosen here over quorum stores.
4. Partition detection via heartbeats and suspicion, false positives versus slow detection.
5. Redelivery bursts on heal and idempotent convergence.
6. Fault injection principles: blast radius control, hypothesis, abort conditions, and learning reviews.

### Sources

Use consistent hashing literature summaries plus official docs for the chosen hash approach conceptually, Redis style expiry documentation for presence correctness, NATS documentation for consumer behavior on disconnect and reconnect, Toxiproxy style tool documentation for fault types, plus one deepening reading on partitions from Designing Data Intensive Applications and the original CAP paper introduction for vocabulary. Keep math light and focus on observable behavior.

### Acceptance Criteria

- With a declared placement function, adding or removing a game node reassigns only a bounded fraction of future matches with no existing healthy match migrating mid fight, verified by mapping comparison described in words.
- During a full partition between one game node group and presence, affected matches abort cleanly after expiry while other nodes continue hosting healthy matches, lobby stays available, and no new clients are routed to the partitioned group after expiry.
- During bus partition from persistence, ticks stay healthy, consumer lag grows, and on heal all pending outcomes converge with single effect and no rating drift.
- During latency injection on the durable path, deadlines and shedding preserve tick health with open degradation signals rather than silent stalls.
- Each drill has a written hypothesis, abort condition, observed result, and one hardening follow up, forming a mini chaos log.

### Interview Gate, Example Questions

- Whiteboard your placement function and show why a membership change moves only a bounded slice of future rooms.
- What would happen if presence expiry were infinite during a partition, and which phantom routing failure would users see.
- Why did you choose open degradation with clean abort over waiting indefinitely for heal, and what genre property makes that acceptable.
- What would happen on heal if consumers were not idempotent, and which metric would first reveal double apply.

### Anti-goals With Why

- Do not add multi region or true multi host networking yet. Why: single host logical partitions already teach detection, expiry, and convergence without cloud cost and noise.
- Do not add consensus or leader election yet. Why: expiry plus idempotency plus deterministic placement solve the required problem with less machinery, consensus is a later study path beyond this roadmap.
- Do not promise zero abort matches under partition. Why: honest partial availability with clean abort is the correct laptop scale trade off, zero abort would require migration which is out of scope by lock.

## STAGE SEVEN — SOAK, LOAD, HARDENING, AND GRADUATION

Timebox: three weeks.

### Scenario

Prove the system under sustained load and graduate. Run the full topology with twenty concurrent matches and one hundred twenty clients plus one hundred headless bots that join queue, play with randomized intents, disconnect and reconnect, and tolerate aborts by requeueing. Soak for an extended duration that exceeds a single match lifetime by an order of magnitude, with at least one rolling node termination and at least one injected partition mid soak. Harden based on findings: tune caps, timeouts, expiry, consumer concurrency, connection pool sizes, and dashboard thresholds. Freeze operating notes for everyday use: startup order, healthy graph shapes, drill playbook, and recovery checklist described in words. End with a final defense covering the entire arc.

Headless bots are first class validators here, not xdotool style hacks. They exercise queue, presence, placement, ticks, events, and durability under churn.

### The Why, Pain Point

This stage exposes long tail issues: slow leaks, backlog creep, file descriptor exhaustion, metric storage growth, consumer lag under churn, and flapping readiness. Short tests hide them. Soak reveals them. It teaches capacity planning on constraint, that sixteen gigabytes forces explicit caps and retention choices, and that resilience is proven by sustained behavior plus injected failure, not by a green single run.

### Concepts To Study, In Order

1. Load versus soak versus spike versus chaos, what each proves.
2. Bottleneck analysis with use and saturation, finding the true constraint on the laptop.
3. Queuing intuition, Little style reasoning without heavy math: backlog equals arrival rate times wait.
4. Resource leaks and saturation over time, how to read slow drift on graphs.
5. Capacity planning and caps, why explicit limits beat hopeful scaling.
6. Incident review writing, hypothesis, timeline, root cause, action with owner.

### Sources

Use Prometheus and Grafana documentation for long retention queries and soak dashboards, NATS and presence store docs for consumer concurrency and connection tuning, PostgreSQL documentation for pool sizing and vacuum awareness at an operator level, plus one deepening chapter on capacity and incident review from a site reliability text. Revisit Designing Data Intensive Applications partitioning chapter for final vocabulary consolidation.

### Acceptance Criteria

- A sustained soak with the full bot plus client target completes with lobby continuously available, healthy matches completing and recording durable results, and partitioned or terminated node matches aborting cleanly with requeue success above a declared threshold described in words.
- Mid soak injection of one node termination plus one partition does not cascade to healthy nodes, does not corrupt ratings, and converges on heal with single effect outcomes.
- Resource graphs over the soak show bounded memory, bounded backlog, and bounded storage growth with no unbounded drift, or a written leak note with cap mitigation.
- Operating notes exist describing healthy versus unhealthy graph shapes, startup order rationale, and recovery steps for the three practiced faults, written for a future self after a month away.
- Final defense passes on Explain Decide Predict across all stages with emphasis on trade offs accepted due to single host constraint.

### Interview Gate, Example Questions, Final Defense Sample

- Whiteboard the entire request to result path under partition and point to every bound that prevents cascade.
- What would happen if bot arrival rate doubled with the same caps, and where would the system say no first.
- Why did you choose clean abort plus requeue over migration or waiting, and what would have to change in genre or scale to revisit that.
- What is the single most misleading graph in your dashboards and how do you avoid fooling yourself with it.
- What would you change first with ten times the hardware, and what would you deliberately keep the same.

### Anti-goals With Why

- Do not chase higher concurrent counts beyond the laptop target to impress. Why: beyond target you measure host exhaustion, not architecture, and you risk learning the wrong lesson.
- Do not add new topology during soak. Why: soak measures stability, new primitives reset the clock and hide drift.
- Do not automate graduation by green dashboards alone. Why: the final defense requires reasoning about trade offs, not just passing graphs.

## 6. Graduation Definition

Graduation requires all stage gates passed in order, soak completed with mid soak faults survived, operating notes written, chaos log complete with at least four partition or termination drills, and final defense passed. The builder should then be able to whiteboard authoritative ticks, presence with expiry, event decoupling with idempotent convergence, bounded retries with graceful shutdown, deterministic placement with open degradation under partition, and capacity reasoning on constraint, each with a named trade off and a named alternative rejected.

Suggested next study beyond this roadmap, not part of v1.0: consensus and leader election, multi instance durable stores with quorum, true multi host networking, and client prediction with reconciliation. Those build on this base without invalidating it.

---

## 7. Risks And Non Goals

Single host simulation cannot prove geographic latency, availability zone independence, or true split brain across data centers. It proves habits and mechanisms that transfer. Bot behavior approximates but never equals human play bursts. Metric retention on sixteen gigabytes forces short windows and aggressive downsampling, which is itself a useful constraint lesson. No commercial launch readiness is claimed. Security hardening, cheat prevention, and payment flows are explicitly out of scope.
